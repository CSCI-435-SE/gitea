# routers/private, routers/install and cmd — hooks, installer, CLI

**Read when:** working on git hooks, the push path's server side, the first-run installer, or a
CLI subcommand.
**Not here:** the push fan-out logic -> `services-repository.md`; web routes -> `routers-web.md`.

## Responsibilities

| Path | Role |
| --- | --- |
| `routers/private` | the **internal** API, called by `cmd/serv.go` and the git hooks running on the server. Not reachable from outside. |
| `routers/install` | the first-run installer pages, served instead of the normal routes until setup completes |
| `cmd` | every CLI subcommand: `web`, `serv`, `hook`, `doctor`, `admin *`, `dump`, `migrate`, `manager`, `actions` |

## Key files

| Path | What it holds |
| --- | --- |
| `routers/private/hook_pre_receive.go` | accepts or rejects a push (branch protection, quotas) |
| `routers/private/hook_post_receive.go` | after a push: `SyncBranchesToDB`, then `PushUpdates` |
| `routers/private/hook_proc_receive.go` | AGit flow (`services-pull-and-gitdiff.md`) |
| `routers/private/serv.go`, `key.go` | SSH access decisions for `cmd/serv.go` |
| `routers/private/internal.go` | the internal-auth middleware |
| `routers/private/manager.go` | runtime management used by `cmd/manager.go` |
| `cmd/web.go` | starts the server — the normal entry point |
| `cmd/serv.go` | invoked by SSH for every git-over-SSH operation |
| `cmd/hook.go` | the binary the installed git hooks call |
| `cmd/doctor.go` | the self-check and repair commands |

## Conventions & invariants

- **The git hooks installed in each repository call the Gitea binary** (`cmd/hook.go`), which calls
  the internal API in `routers/private` over HTTP. That indirection is why push logic lives in
  services, not in the hook.
- `routers/private` is protected by an internal token, not user auth. It must never be mounted
  publicly, and handlers there take `*context.PrivateContext` (`services-context.md`).
- **`hook_pre_receive` is the enforcement point** for anything that must *prevent* a push — branch
  protection, size limits. `hook_post_receive` reacts to a push that already happened and cannot
  reject it.
- The push path runs inside the user's `git push`, so latency there is user-visible
  (`services-repository.md`).
- `cmd` is the leftmost layer (`architecture.md`): it may import anything, and nothing imports it.
- A new CLI subcommand is a file in `cmd/` registered with the others in `main.go`; most have a
  `*_test.go` beside them.

## Recipes

**Reject a push under a new condition.** `routers/private/hook_pre_receive.go`, with the rule
itself in a service so the web UI can apply the same check.

**Add a CLI subcommand.** New `cmd/<name>.go` following a neighbour's structure, registered in
`main.go`, with a `_test.go`.

**Add a doctor check.** `services/doctor` holds the checks; `cmd/doctor.go` only exposes them.

## Gotchas

- Hooks run as a separate process invocation, so they do not share memory, caches or the request
  context with the web server — everything goes over the internal API.
- Changing the internal API is a compatibility concern *within one install*: the hook scripts on
  disk are regenerated by `SyncRepositoryHooks` (`services-repository.md`), so a mismatch after an
  upgrade is a real failure mode.
- The installer routes are mounted *instead of* the normal ones before setup; `routers/init.go`
  switches between them.
